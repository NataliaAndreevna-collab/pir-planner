## 1. Что это за программа

FastAPI-бэкенд (`app/main.py`) + статический интерфейс (`app/static/index.html`, `app.js`, `kp.js`), развёрнут на Render (`pir-planner.onrender.com`).
По тексту технического задания (ТЗ) программа:
1. определяет состав проектной (ПД) и рабочей (РД) документации по ПП РФ № 87 и ГОСТ Р 21.101;
2. строит календарный график работ (с экспертизой, согласованиями с заказчиком, реестром замечаний ГИПа), выгрузка в Excel и Word;
3. считает стоимость ПИР (смета, Excel) и формирует коммерческое предложение (КП, Word).

Два движка разбора ТЗ: `local` (регулярки, `tz_parser.py`, `pp87_rules.py`) и `ai` (OpenRouter, `llm_parser.py`, по умолчанию Gemini 2.5 Flash). Ключ `OPENROUTER_API_KEY` в `.env`, в репозиторий не попадает.

## 3. Что сделано

**Парсер ТЗ.** «Только РД» распознаётся; график не падает без ПД; таблица ТЗ «№ | Поле | Значение» читается (объект, заказчик, подрядчик, договор, дата), даже если в строке потерян номер; дата договора не захватывает лишнее; «5 км» не считается маркой КМ; «Проектная документация и рабочая документация» даёт ПД+РД.

**Смета и КП** (восстановлены из коммита `37fbbf8` после случайного удаления другой моделью). Три независимых метода: по сборникам МНЗ/СБЦП (`data/normative_catalog.json`, 15 сборников, 72 позиции), по трудозатратам (методика 707/пр), по рыночным окладам специалистов; справочный расчёт от СМР. Исправлено то, что считало «молча»:
- нет автоподстановки сборника и X, список позиций по умолчанию пуст, X вводится вручную (0 → 0 ₽ и предупреждение);
- нет скрытых сумм (3 000 000 ₽, зашитые суммы изысканий и др.); дополнительные работы никогда не включаются автоматически;
- НДС: 5% по умолчанию, 22% (с 2026 года), без НДС;
- все предупреждения в жёлтом блоке вкладки и в Excel;
- вкладка расчёта строится сама при открытии и сбрасывается при загрузке нового ТЗ.

**Трудозатраты (методы 2А и 2Б)** считаются по черновым нормам человеко-дней на раздел, `data/labor_norms.json` (`approved: false`). Это оценка, не норматив; пока не утверждено, показывается предупреждение. Таблица пересобирается по составу разделов, пока пользователь не правил её вручную.

**Этап Б, маскирование** (`app/services/masking.py`). Перед отправкой в ИИ заменяются: заказчик, подрядчик, номер и дата договора, название объекта (и его короткие варианты), ФИО, адреса, ИНН/КПП/ОГРН/счета/БИК, почта, телефоны, блоки подписей. Город и регион остаются. Реквизиты в ответе ИИ игнорируются: их заполняет локальный парсер. Проверить, что уйдёт: `POST /api/preview-ai-payload` на странице `/docs`. Окна предпросмотра в интерфейсе нет (пользователь не хочет его в финале).

**Этап Б, ИИ-подбор** (`app/services/ai_cost.py`, эндпоинты `/api/ai-suggest-collections` и `/api/ai-fill-x`, две кнопки на вкладке расчёта):
1. «Подобрать позиции по ТЗ (ИИ)»: ИИ находит объекты и выбирает позиции справочника; только существующие id; «нет подходящей позиции» сообщается явно; X не заполняется.
2. «Найти X в ТЗ (ИИ)»: запрос только для строк, где X не определён; ручные и подтверждённые значения не запрашиваются; ИИ должен дать цитату и перевод единиц; **число проверяется по тексту ТЗ**, выдуманное отклоняется.
3. Если X в ТЗ нет: берётся минимальное X нижнего интервала таблицы с пометкой «данные не указаны в ТЗ, уточните у заказчика» (в интерфейсе и в смете).
4. Смена сборника/таблицы в строке сбрасывает X и помечает строку «требует повторного запроса».
ИИ-запросы только по явному нажатию кнопки, не по умолчанию.

## 4. Известные проблемы

1. **Математика расчёта не соответствует реальности** из-за нехватки данных. Методы 2А и 2Б опираются на черновые нормы. У пользователя уже есть собственный готовый модуль расчёта (см. п. 5), его нужно изучить.
2. Справочник покрывает воду, дороги, здания, связь и т.п. Позиций для объектов защиты от БПЛА (противодронные комплексы, габионные стены) в нём нет, ИИ по ним ответит «нет позиции». Для таких работ основной метод по сборникам не применим.
3. ~~Движок `engine=ai`: флаги экспертизы жёстко `True`~~ исправлено: флаги следуют полю `has_expertise` из ответа нейросети (если поля нет, остаётся включено).
4. `explicit_pd` / `explicit_rd` ищутся по всему тексту ТЗ, включая список защищаемых объектов; возможны лишние разделы.
5. Парсер нестабильно распознаёт очень короткие искусственные ТЗ (две-три строки); тесты построены на реальном ТЗ (`tests/fixtures/tz_tec1_rd_only.txt`, анонимизировано).
6. Маскирование работает по шаблонам и не даёт гарантии; опечатки в названии объекта («ТТЭЦ-1» вместо «ТЭЦ-1») оно не ловит полностью.
7. Этап Б не проверен на настоящем OpenRouter (в тестах нейросеть подменена заглушкой), интерфейс этапа Б не проверен в браузере.

3. **Отладка трудозатрат по выполненным контрактам**: взять фактические человеко-дни и стоимость по разделам из завершённых проектов, заполнить `data/labor_norms.json`, поставить `approved: true`. Пока данных нет, основным считать метод 1 (по сборникам).
4. Открыть pull request из `stage-b-masking` (она содержит этап А) в `feature/cost-module` после проверки; настроить на Render нужную ветку.
5. Дефект п. 4.4 (лишние разделы из списка объектов) не тронут: на реальных ТЗ не проявился, правка затрагивает основной разбор. Исправлять при появлении жалобы, с тестом на реальном ТЗ.
6. При необходимости расширить справочник позициями для типовых объектов бюро (в том числе защита от БПЛА), если для них есть расценки.
